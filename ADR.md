# Architecture Decision Records (ADR)

This file collects the **Architecture Decision Records** for FED Play — short,
immutable records of significant technical decisions, the context behind them,
and their consequences. New ADRs are **appended**, never edited (except for
minor typo fixes); superseded ones are marked with a pointer to the successor.

> Format adapted from Michael Nygard's ADR template. See
> [GOVERNANCE.md](GOVERNANCE.md) for when an ADR is required (any non-trivial
> structural change, and *always* for changes to the no-build philosophy).

## How to write an ADR

Copy the template at the bottom of this file, append it, and fill it in. Use
the form `ADR-NNNN: short title`. Number sequentially. Keep it to a page or
two. Link related issues/PRs.

## ADR-0001: Zero-build, plain HTML/CSS/vanilla-JS front end

- **Status**: Accepted
- **Date**: 2025-01-01 *(replace with real date)*

### Context

FED Play is a catalog UI for sideloadable apps. It needs to be trivially
hostable on any static host (S3, GitHub Pages, Netlify, even `file://`), easy
for non-expert contributors to extend (mostly just editing a `data.js` array),
and fast to develop without tooling overhead.

### Decision

We will build FED Play as a **zero-build static front end**: plain HTML,
vanilla CSS, and vanilla JavaScript organized as IIFE modules (`FED`,
`FED_LAYOUT`, and the `APPS` data array). No bundler, no framework, no
transpilation, no `package.json`, no runtime dependencies beyond CDN-referenced
fonts/icons/payment SDKs.

### Consequences

- ✅ Anyone can clone and `open index.html` (or `python3 -m http.server`).
- ✅ Contributing an app is a single `data.js` edit — no toolchain to learn.
- ✅ Deployable anywhere static; no server cost.
- ⚠️ We forgo module systems, type checking, and tree-shaking. We mitigate
  with strict conventions (escaping, design tokens) and manual verification.
- ⚠️ Code organization relies on discipline (one IIFE per concern) rather than
  enforced modules.

### Related

[GOVERNANCE.md](GOVERNANCE.md) (philosophy changes need an ADR),
[CLAUDE.md](CLAUDE.md), [AGENTS.md](AGENTS.md).

## ADR-0002: Shared chrome injected by `layout.js`

- **Status**: Accepted
- **Date**: 2025-01-01 *(replace)*

### Context

Ten pages share identical top bar, sidebar, categories bar, toast container,
back-to-top button, and payment modal. Duplicating this in every HTML file
would bloat the repo and make UI changes error-prone (you'd edit ten files).

### Decision

All shared chrome is generated by the `FED_LAYOUT` module in `layout.js` and
injected into each page via `FED_LAYOUT.inject()`. Each HTML page contains
**only** its unique body content plus a small `window.FED_PAGE` config and the
two initialization calls.

### Consequences

- ✅ One place to change shared UI (`layout.js`).
- ✅ Pages stay small and readable.
- ⚠️ Pages require JS to render chrome; non-JS fallback is out of scope.
- ⚠️ New shared elements must be added to the injector, not pasted into pages.

### Related

`layout.js`, [CLAUDE.md](CLAUDE.md) §"Keep HTML pages lean".

## ADR-0003: Per-page `window.FED_PAGE` config object

- **Status**: Accepted
- **Date**: 2025-01-01 *(replace)*

### Context

Each tab needs different active sidebar state, featured apps, and grid
title/subtitle, without a router or build-time config.

### Decision

Each page declares a `window.FED_PAGE = { tab, featuredIds, gridTitle,
gridSub, welcome }` object before calling `FED.init()`. The `FED` module reads
it to drive rendering.

### Consequences

- ✅ Adding a tab = copy a page + edit one config object. No routing layer.
- ✅ `featuredIds` lets curators highlight different apps per tab.
- ⚠️ Config shape is implicit; a future ADR may formalize it if it grows.

### Related

`app.js`, `data.js` (`featuredIds` reference app `id`s).

## ADR-0004: Single `APPS[]` catalog with multi-tag visibility

- **Status**: Accepted
- **Date**: 2025-01-01 *(replace)*

### Context

Apps often belong to multiple tabs (e.g. an app can be both *Creative* and
*Missing*). We want one source of truth, not per-tab duplicated lists.

### Decision

The entire catalog lives in one `APPS[]` array in `data.js`. Each entry has a
`tags` array controlling which tabs/grids it appears on, plus a single
`category` for its accent color and label.

### Consequences

- ✅ One source of truth; dedup is easy (unique `id`).
- ✅ Cross-tab apps need a single entry.
- ⚠️ `tags` values are an implicit vocabulary; a verification script should
  flag unknown tags (see [ROADMAP.md](ROADMAP.md)).

### Related

`data.js`, [CONTRIBUTING.md](CONTRIBUTING.md) app-entry checklist.

## ADR-0005: Escape all cataloged strings; `https://`-only download URLs

- **Status**: Accepted
- **Date**: 2025-01-01 *(replace)*

### Context

The catalog is partly community-editable and renders into the DOM. Unescaped
strings or unsafe URL schemes could enable XSS or `javascript:` link attacks.

### Decision

All cataloged strings inserted into the DOM pass through `escapeHtml()` in
`app.js`. New rendering paths must escape. `downloadUrl` values must be
`https://`; `javascript:`/`data:` schemes are rejected/stripped. This is a
security boundary documented in [SECURITY.md](SECURITY.md).

### Consequences

- ✅ Defense-in-depth against injection from catalog data.
- ⚠️ Requires discipline on every new render path; a lint/check should enforce
  it (planned).

### Related

`app.js`, [SECURITY.md](SECURITY.md).
